# 07｜紀錄檔格式（流程結束時產出的兩份 log）

## A. 訪綱決策紀錄（給 mentor／管理者 討論用）

**產出時機**：各場訪綱全部確認後，隨訪綱檔案一併交付；有寫回 Notion 時，同步在訪綱目錄頁下建一頁。
**目的**：使用者帶著訪綱與這份紀錄，向**不在同一專案裡的 mentor／管理者**說明「為什麼這樣設計」——mentor／管理者 不需要翻專案文件就能快速進入狀況、聚焦給意見。寫作原則：假設讀者對本專案零認知。

格式：

```
# 訪綱決策紀錄｜{專案名稱}
產出日期／使用者／題庫版本（reference 最後更新日）

## 1. 專案背景摘要（列點呈現，讓不在專案內的人看得懂）
客戶與產業／要做什麼／目前階段／已知的關鍵背景與限制——
一項一點，不寫成連續長段落

## 2. 定位判讀
- 象限：{使用對象 × 專案模式}＋判讀依據
- 加掛模組：品牌形象（掛／不掛＋依據）、系統限制釐清（優化版／建置版）
- 利關人結構理解：主需求單位、有無關鍵決策者、高層時間狀況

## 3. 利關人名單與執掌（輸入資料彙整）
第一次輸入（或專案頁本來就有）的利關人名單與執掌資料原文節錄，
依面向／群組列點——讓 mentor／管理者 直接看到未經口語轉化的原始背景；
輸入沒有執掌資料的單位如實標注「無執掌資料」

## 4. 場次規劃與理由
場次規劃表＋拆場邏輯說明（為何這樣合併／拆分、順序理由、固定約束、
場數與時長的取捨）——邏輯說明列點呈現，一個決策一點

## 5. 各場設計重點
每場 2–3 句：這場的比重放在哪、為什麼；有做哪些客製調整

## 6. 刪減與取捨
各場被自動刪減的題目清單與刪減理由（時長限制／與專案關聯較低）

## 7. 給主訪的備註
開放題輸入轉換出的執行提醒（不在訪綱本體內的那些）

## 8. 建議與 mentor／管理者 討論的點（本紀錄最重要的一節）
誠實列出：判讀時拿不準的地方、兩可的取捨、依賴假設的決定、
建議人工再確認的部分。寧可多列，不要展示信心。
```

**內部術語白話化紀律**：讀者假設對本專案**與題庫規則**皆零認知——紀錄中提到模組名、規則名或內部判讀用語（如「主象限模組」「窗口觀察視角」「合併場折減」）時，必須先用白話把這句話的含義寫清楚（它實際上代表什麼做法、為什麼這樣做），讓人一眼看懂；規範檔案名稱可附註供有需要時再檢索，但不能要求讀者先讀規則才看得懂這份紀錄。

**引用專案資料的寫法紀律**：轉述輸入資料時，區分「資料明載」與「資料中的舉例／自行歸納」——來源寫的是舉例（「ex⋯等」）或流程面向，就不能寫成看起來像定案清單；必要時標注「（專案頁舉例）」「（涵蓋⋯等流程面向，非逐一名稱）」。讀者要能從寫法分辨哪些是確切資料、哪些不是。

## B. skill 使用 log（即時追加式，給 skill 維護者分析用）

**運作方式（不做「流程結束」判定）**：流程第一步就建立 log 檔，之後**每個事件發生當下即追加一條**——包含寫回 Notion 之後使用者的任何後續調整。log 永遠是最新狀態，維護者要分析時直接取用當下的檔案即可；彙整與摘要不在 log 的職責內，由拿到 log 的人事後再請 AI 做。
**目的**：讓 skill 維護者事後分析使用過程，找出規則缺口與優化點。**不寫入 Notion 專案頁**（屬工具改善資料，不是專案文件）。
**命名**：`YYYYMMDD_專案名_需訪log.md`（例：`20260724_田原香_需訪log.md`）。**訪綱產出檔的命名規則維持現行版本（見 01 文件標題規則），不做變動。**
**交付**：隨每一批產出（訪綱交付、寫回完成）一併附上當下版本，並提醒使用者集中存放。

**格式（純事件流水帳，一事件一條，不彙整）**：

```
# skill 使用 log｜{專案名稱}｜{起始日期}

[01] 啟動｜使用者輸入原文：「⋯」
[02] 讀取｜抓取專案頁 {連結}；自動判讀到：{欄位清單}；缺漏：{欄位清單}
[03] 提問｜向使用者詢問：{內容}
[04] 使用者回覆｜原文逐字：「⋯」
[05] 修改要求｜原文逐字：「⋯」→ 對應調整：{做了什麼}
[06] 規則邊界｜{情境} 規則未定義，本次採 {解讀}
[07] 判讀確認｜提出：{判讀摘要} → 使用者：{確認／修正內容}
[08] 產出｜{檔名}；{題數}；被刪題：{清單或無}
[09] 寫回｜Notion 位置：{連結}
[10] 事後調整｜原文：「⋯」→ 調整：{內容}
...（持續追加）
```

事件類型：啟動／讀取／提問／使用者回覆／修改要求／規則邊界／判讀確認／產出／寫回／事後調整。**使用者的回覆與修改要求一律逐字保留，禁止摘要改寫。**

**追加紀律（append-only）**：log 條目嚴格 append-only、編號遞增。事後補寫或修訂既有條目時，以新條目「[N-補記]」或「[N-修訂]」形式追加於文末，**不得插入原編號位置**，以保留事件實際發生的時序。
